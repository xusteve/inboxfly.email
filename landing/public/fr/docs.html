1. Démarrage rapide en local (3 min)

Les environnements locaux ne peuvent pas recevoir de vrais e-mails, mais vous pouvez tester tout le panneau et le pipeline (données via « Simuler ») :

git clone https://github.com/INBOXFLY-REPO-PLACEHOLDER/inboxfly.git
cd inboxfly && npm install
npm run dev          # 启动在 http://localhost:8787
  • La première visite ouvre l’assistant de configuration ; le SETUP_TOKEN local est inboxfly-local-setup (voir .dev.vars).
  • L’étape 3 de l’assistant (Activer Email Routing) est ignorée localement.
  • Dans le panneau, cliquez sur « Simuler » : cela injecte des e-mails de test via exactement le pipeline de production (correspondance → filtre → décision → stockage → statistiques), en sautant seulement la livraison réelle.
  • Pour réinitialiser : rm -rf .wrangler puis redémarrez, puis refaites l’assistant.

2. Déployer sur Cloudflare

npx wrangler login
npx wrangler deploy           # Worker + 静态面板 + D1 + R2 + KV + Cron
npx wrangler secret put SETUP_TOKEN    # 首次运行向导用的初始化令牌
  • Les tables D1 sont créées automatiquement à la première visite du panneau — aucun SQL manuel requis (ou exécutez npx wrangler d1 execute inboxfly --remote --file schema.sql en secours).
  • Le panneau est par défaut à https://inboxfly.<votre-sous-domaine>.workers.dev ; liez un domaine personnalisé (ex. panel.yourdomain) sous Workers → Domains & Routes.
  • Le Cron Trigger (nettoyage R2 quotidien à 03:00 UTC) est enregistré automatiquement avec le déploiement.
  • robots.txt inclut Disallow: / pour que votre panneau privé ne soit pas indexé.

3. Assistant de première exécution (5 étapes)

Ouvrez l’URL du panneau après le déploiement et suivez l’assistant. Chaque étape explique le « pourquoi » et les « risques » :

  1. Vérifier l’identité du déployeur: saisir le SETUP_TOKEN (n’apparaît que dans la sortie du déploiement, invalidé après configuration) pour empêcher la prise de contrôle.
  2. Créer les identifiants admin: nom d’utilisateur + mot de passe ≥8 caractères (haché PBKDF2, non récupérable).
  3. Activer Email Routing: ignorer en local ; en production suivre le guide du tableau de bord Cloudflare (section suivante).
  4. Ajouter une adresse de destination: saisir votre vraie boîte mail (ex. Gmail) et terminer la confirmation Cloudflare.
  5. Créer la première règle: par défaut *@yourdomain → transférer → destination vérifiée, et la définit comme repli fail-open.

4. Activer le routage email (par domaine)

Trois éléments doivent être en place : l’interrupteur principal Email Routing, le catch-all pointant vers le Worker et une destination vérifiée. Deux façons :

Option A · Automatisation par le panneau (recommandée)

Après avoir enregistré un jeton API CF dans Paramètres → Domaines, un bouton « Activer le transfert » apparaît par domaine. Le panneau : détecte les conflits MX (les liste pour confirmation par enregistrement) → active Email Routing → ajoute les enregistrements DNS MX/SPF recommandés → pointe catch-all vers le Worker InboxFly.

Permissions du jeton (testées) : Compte → Workers Scripts / D1 / KV / R2 Storage (Modifier) + Paramètres du compte (Lire) ; Zone → Zone (Lire), DNS (Modifier), Email Routing Rules (Modifier), Zone Settings (Modifier). Note : activer/interroger Email Routing nécessite le groupe « Zone Settings », pas « Email Routing Rules » — cochez les deux sinon erreur Authentication.

Option B · Manuellement dans le tableau de bord Cloudflare

Tableau de bord → votre zone → Email → Email Routing → Activer (confirmer le remplacement MX) → Adresse catch-all → action « Send to a Worker » → choisir inboxfly. Actualisez ensuite le panneau ; toutes les vérifications passent au vert.

5. Adresses de destination

  • Ajoutez votre vraie boîte mail sur la page Destinations → Cloudflare envoie automatiquement un e-mail de confirmation → dès que le destinataire clique, le panneau passe à « Vérifié ».
  • Les destinations sont au niveau du compte : vérifiez une fois, utilisez partout.
  • La première adresse vérifiée devient le repli fail-open : le Worker la tente en cas d’erreur interne pour éviter toute perte silencieuse.
  • Les adresses référencées par des règles ne peuvent pas être supprimées (il vous sera demandé de modifier la règle d’abord).

6. Règles de routage

La page des règles reflète la page de routage native de Cloudflare : un tableau unifié avec une ligne de repli fixe « 📌 Catch-all » en fin.

Créer une règle

  • Correspondance email : nom à gauche (ex. info, support) + @ + liste de domaines à droite ; nom vide = tout le domaine.
  • Action : Envoyer à un email (transférer vers une destination vérifiée) / Supprimer (silencieux) / Rejeter (amélioration InboxFly — refus au niveau SMTP, pas disponible nativement).
  • Filtres avancés (améliorations optionnelles) : blacklist expéditeur (un par ligne : adresse / @domaine / /regex/), regex d’objet, limite de taille (≤25Mo), condition de pièce jointe.

Ordre d’évaluation

Règles exactes → règles catch-all, triées dans le groupe, premier match gagnant. Les e-mails non matchés vont à la ligne Catch-all (transférer par défaut / rejeter / supprimer).

Important : ne créez pas de règles de routage manuellement dans le tableau de bord Cloudflare — les règles natives priment sur catch-all et contournent InboxFly (ni copies, ni statistiques). Importez les règles natives existantes via Paramètres → Domaines.

7. Gestion quotidienne

  • Liste des e-mails : filtre par domaine / statut / mot-clé ; suppression par lot multi-sélection prise en charge.
  • Détail de l’e-mail : rendu HTML sandboxé (images distantes bloquées), affichage texte, téléchargements de pièces jointes, MIME brut (.eml).
  • Statistiques : par statut (transféré/bloqué/supprimé/rejeté/erreur) et domaine, avec tendances sur 14 jours. « Transféré » = Cloudflare a accepté le transfert ; le placement final n’est pas observable.
  • Disposition : le bouton en haut à droite bascule entre les modes barre latérale / en-tête ; mobile utilise toujours la disposition en-tête.

8. Stockage & quotas

  • Les copies (HTML/texte/MIME brut) et pièces jointes vivent dans votre propre R2, conservées 30 jours par défaut avec nettoyage automatique quotidien à 03:00 UTC (réglable dans Paramètres ; nettoyage manuel disponible).
  • Les e-mails bloqués par filtre stockent uniquement les métadonnées par défaut (anti-déluge de spam) ; activez les corps complets si besoin.
  • Un bandeau d’avertissement apparaît quand l’estimation R2 sur 30 jours dépasse 9Go, avec bascule en un clic vers le mode métadonnées seules (transfert inchangé).

9. Sécurité

  • Cloudflare Turnstile : Paramètres → Protection anti-bots, collez les clés Site/Secret et activez — une vérification humaine apparaît à la connexion (siteverify côté serveur). Pour les tests locaux, clés de test officielles : Site 1x00000000000000000000AA / Secret 1x0000000000000000000000000000000AA (toujours valide).
  • Compte admin : Paramètres → Compte admin ; changer nom/mot de passe invalide toutes les autres sessions.
  • Sessions : 24h par défaut, 30 jours avec « rester connecté » ; protection CSRF sur les modifications, connexion limitée en débit.
  • Sécurité du contenu : les corps sont rendus dans une sandbox iframe (scripts désactivés), l’assainissement serveur retire le balisage dangereux, images distantes bloquées par défaut.

10. Thèmes / langue / PWA

  • 3 thèmes × clair/sombre : Fluid Glass (défaut) / Minimal / Playful, chacun avec variante sombre complète ; suit le système par défaut.
  • 10 langues : détection automatique depuis le navigateur ; bascule à tout moment via l’icône globe.
  • Installation PWA : Android Chrome → menu « Installer l’application » (ou bouton Paramètres) ; iOS Safari → Partager → « Ajouter à l’écran d’accueil ».

11. Limites connues

  • Le local ne peut pas recevoir de vrais e-mails (Email Routing est une fonctionnalité de production) — utilisez « Simuler » en local.
  • « Transféré » signifie que Cloudflare l’a accepté ; le placement dans le dossier spam n’est pas observable. Mettez votre domaine en liste blanche dans la boîte du destinataire si nécessaire.
  • Ne mélangez pas les règles natives Cloudflare et InboxFly sur le même domaine (elles contournent le panneau) ; la coexistence au niveau de la zone est sans problème.
  • 25MiB par message (limite de la plateforme Cloudflare).

12. Désinstallation & nettoyage

  1. Révoquez le jeton API CF du panneau (tableau de bord → Jetons API) — le pipeline de transfert fonctionne indépendamment dans votre compte et continue ; l’automatisation du panneau se dégrade.
  2. Arrêter le transfert : tableau de bord → Email Routing → désactiver Catch-all ou tout le service.
  3. Supprimer les ressources : Workers → inboxfly ; D1 → inboxfly ; R2 → inboxfly ; KV → le namespace.
Si quelque chose n’est pas couvert ici, ouvrez un ticket GitHub (lien du dépôt sur la page produit).

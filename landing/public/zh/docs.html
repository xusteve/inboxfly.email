1. 本地快速体验（3 分钟）

本地无法接收真实邮件，但可以体验完整的管理面板与处理管道（用「模拟收信」注入测试数据）：

git clone https://github.com/INBOXFLY-REPO-PLACEHOLDER/inboxfly.git
cd inboxfly && npm install
npm run dev          # 启动在 http://localhost:8787
  • 首次打开会进入首次运行向导，本地 SETUP_TOKEN 为 inboxfly-local-setup（定义在 .dev.vars）。
  • 向导第 3 步「激活 Email Routing」在本地直接跳过。
  • 进入面板后点「模拟收信」：会用与生产完全相同的管道（匹配 → 筛选 → 决策 → 存储 → 统计）生成测试邮件，仅跳过真实投递。
  • 重置环境：rm -rf .wrangler 后重启，即可重新走向导。

2. 部署到 Cloudflare

npx wrangler login
npx wrangler deploy           # Worker + 静态面板 + D1 + R2 + KV + Cron
npx wrangler secret put SETUP_TOKEN    # 首次运行向导用的初始化令牌
  • D1 数据表在面板首次访问时自动创建，无需手工执行 SQL（也可 npx wrangler d1 execute inboxfly --remote --file schema.sql 手动兜底）。
  • 面板访问地址默认是 https://inboxfly.<你的子域>.workers.dev；建议在 Workers → 域名与路由 中为 Worker 绑定一个自定义域（如 panel.你的域名）。
  • Cron Trigger（每日 03:00 UTC 的 R2 过期清理）随部署自动注册。
  • robots.txt 已内置 Disallow: /，私有面板不会被搜索引擎索引。

3. 首次运行向导（5 步）

部署后打开面板 URL，按向导完成初始化。每一步都会说明「为什么需要」与「风险与后果」：

  1. 验证部署者身份：输入 SETUP_TOKEN（只在部署输出中出现，完成后作废），防止他人抢先接管面板。
  2. 创建管理员凭证：用户名 + ≥8 位密码（PBKDF2 哈希存储，不可找回）。
  3. 激活 Email Routing：本地跳过；生产环境按引导在 Cloudflare Dashboard 启用（见下一节）。
  4. 添加转发目标地址：填写你的真实邮箱（如 Gmail），完成 Cloudflare 的确认流程。
  5. 创建首条规则：默认生成 *@你的域名 → 转发 → 已验证目标，首个目标地址同时设为故障兜底地址。

4. 启用邮件转发（每个域名）

一条邮件要完成转发，需要三件事就位：Email Routing 总开关、catch-all 指向 Worker、已验证的目标地址。两种方式：

方式 A · 面板自动化（推荐）

在「设置 → 域名」配置 CF API Token 后，域名列表会出现「开启转发」按钮，面板自动完成：MX 冲突检测（有冲突会列出并要求逐条确认）→ 启用 Email Routing → 自动补齐 MX / SPF DNS 记录 → catch-all 指向 InboxFly Worker。

Token 权限清单（实测踩坑）：帐户 → Workers 脚本/D1/KV/R2 存储（编辑）+ 帐户设置（读取）；区域 → 区域（读取）、DNS（编辑）、电子邮件路由规则（编辑）、区域设置（编辑）。注意：启用/查询 Email Routing 的 API 要求的是「区域设置」权限组而非「电子邮件路由规则」——两者都要勾，缺一则报 Authentication error。

方式 B · Cloudflare Dashboard 手动

Dashboard → 你的域名 → 电子邮件 → 电子邮件路由 → 启用（确认 MX 替换）→ Catch-all 地址 → 操作选「发送到 Worker」→ 选择 inboxfly。完成后回到面板刷新，域名体检会全部变绿。

5. 目标地址

  • 「目标地址」页添加你的真实邮箱 → Cloudflare 自动发送确认邮件 → 收件人点击链接后，面板状态自动变为「已验证」。
  • 目标地址是账号级资源：验证一次，所有域名通用，无需重复验证。
  • 首个验证地址会自动设为故障兜底地址（fail-open）：Worker 内部异常时优先尝试它，避免静默丢信。
  • 被规则引用的地址不能删除（会提示先修改规则）。

6. 转发规则

规则页与 Cloudflare 原生路由规则页同一心智：一张统一规则表 + 表尾固定的「📌 全收（Catch-all）」兜底行。

创建规则

  • 电子邮件匹配模式：左侧填名称（如 info、support）+ @ + 右侧选择域名；留空名称 = 整个域名通配。
  • 操作：发送到电子邮件（转发到已验证目标）/ 丢弃（静默删除）/ 退信（InboxFly 增强，SMTP 层拒绝并通知发件人，Cloudflare 原生不支持）。
  • 高级筛选（可选增强）：发件人黑名单（每行一条：完整地址 / @域名 / /正则/）、主题正则、大小上限（≤25MB）、附件条件。

评估顺序

精确地址规则 → 域名通配规则，组内按排序，先匹配先停。都未命中时由全收兜底行处理（转发到默认地址 / 退信 / 丢弃）。

重要：请勿在 Cloudflare 后台手动创建路由规则——原生规则优先于 catch-all，会让对应邮件绕过 InboxFly（无副本、无统计）。域名下已有原生规则时，用「设置 → 域名 → 导入原生规则」一键迁移。

7. 日常管理

  • 邮件列表：按域名 / 处理状态 / 关键词（发件人、主题、正文）筛选与搜索；支持批量多选删除。
  • 邮件详情：HTML 正文沙箱渲染（远程图片默认屏蔽）、纯文本直显、附件下载、原始 MIME（.eml）下载。
  • 统计：按处理状态（已转发/拦截/丢弃/退信/异常）与域名维度汇总，附 14 天趋势。「已转发」= Cloudflare 受理转发；最终落箱位置任何转发服务都无法观测。
  • 布局：邮件页右上角按钮一键切换侧边栏 / 页眉模式；移动端始终使用页眉布局。

8. 存储与配额

  • 邮件副本（HTML/纯文本/原始 MIME）与附件存放在你自己的 R2，默认保留 30 天，每日 03:00 UTC 自动清理（保留天数可在设置中调整，也可在设置中手动触发清理）。
  • 被筛选拦截的邮件默认仅存元数据（防垃圾风暴占满 R2），需要回看时再开启完整存储。
  • R2 用量估算（近 30 天累计）超过 9GB 时面板出现预警横幅，可一键切换「仅元数据」模式（转发不受影响，只是不再存副本）。

9. 安全配置

  • Cloudflare Turnstile：设置 → 机器人防护，填入 Site Key / Secret Key 并开启，登录页即出现人机验证（服务端 siteverify 校验）。本地调试可用官方测试密钥：Site 1x00000000000000000000AA / Secret 1x0000000000000000000000000000000AA（总是通过）。
  • 管理员账户：设置 → 管理员账户，验证当前密码后可改用户名/密码；修改后其他端会话全部失效。
  • 会话：默认 24 小时，勾选「保持登录」为 30 天；所有变更接口有 CSRF 防护，登录有频率限制。
  • 邮件内容安全：正文在 iframe 沙箱中渲染（脚本禁用），服务端消毒剥离危险标签，远程图片默认不加载。

10. 主题 / 语言 / PWA

  • 三套主题 × 深浅色：液态玻璃（默认）/ 极简克制 / 明快活力，各带完整深色变体；深浅色默认跟随系统。
  • 10 种语言：跟随浏览器自动选择，侧栏页脚或页眉的地球图标随时切换。
  • PWA 安装：Android Chrome → 浏览器菜单「安装应用」（或设置页「安装到本机」按钮）；iOS Safari → 分享 → 「添加到主屏幕」。

11. 已知边界

  • 本地环境无法接收真实邮件（Email Routing 是 Cloudflare 生产能力），本地用「模拟收信」验证管道。
  • 「已转发」表示 Cloudflare 受理转发；是否被对方判进垃圾箱不可观测。若送达率不理想，在收件邮箱中把你的域名加入白名单/联系人。
  • 同一域名内请勿混用 Cloudflare 原生规则与 InboxFly（原生规则会让邮件绕过面板），zone 级并存没有问题。
  • 单封邮件上限 25MiB（Cloudflare 平台限制）。

12. 卸载与清理

  1. 撤销授予面板的 CF API Token（CF 后台 → API 令牌）——邮件转发管道由你账号内的 Worker 独立运行，撤销后面板自动化功能降级，转发不受影响。
  2. 停止转发：Cloudflare Dashboard → 电子邮件路由 → 关闭「Catch-all」或整个 Email Routing。
  3. 删除资源：Workers → inboxfly；D1 → inboxfly；R2 → inboxfly；KV → 对应命名空间。

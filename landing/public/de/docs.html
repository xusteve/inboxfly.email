1. Lokaler Schnellstart (3 Min.)

Lokal können keine echten E-Mails empfangen werden, aber das volle Panel und die Pipeline lassen sich testen (Testdaten über „Simulieren“):

git clone https://github.com/INBOXFLY-REPO-PLACEHOLDER/inboxfly.git
cd inboxfly && npm install
npm run dev          # 启动在 http://localhost:8787
  • Der erste Besuch öffnet den Setup-Assistenten; das lokale SETUP_TOKEN ist inboxfly-local-setup (siehe .dev.vars).
  • Assistent-Schritt 3 (Email Routing aktivieren) wird lokal übersprungen.
  • Klicken Sie im Panel auf „Simulieren“: Es speist Test-E-Mails durch exakt die Produktions-Pipeline (Match → Filter → Entscheidung → Speicherung → Statistik) und überspringt nur die echte Zustellung.
  • Zum Zurücksetzen: rm -rf .wrangler und Neustart, dann den Assistenten erneut durchlaufen.

2. Auf Cloudflare deployen

npx wrangler login
npx wrangler deploy           # Worker + 静态面板 + D1 + R2 + KV + Cron
npx wrangler secret put SETUP_TOKEN    # 首次运行向导用的初始化令牌
  • D1-Tabellen werden beim ersten Panel-Besuch automatisch erstellt — kein manuelles SQL nötig (als Fallback npx wrangler d1 execute inboxfly --remote --file schema.sql).
  • Das Panel ist standardmäßig unter https://inboxfly.<dein-Subdomain>.workers.dev; binde unter Workers → Domains & Routes eine Custom Domain (z. B. panel.yourdomain).
  • Der Cron-Trigger (tägliche 03:00-UTC-R2-Bereinigung) wird beim Deploy automatisch registriert.
  • robots.txt enthält Disallow: /, damit dein privates Panel nicht indexiert wird.

3. Ersteinrichtungs-Assistent (5 Schritte)

Öffne nach dem Deploy die Panel-URL und folge dem Assistenten. Jeder Schritt erklärt „Warum“ und „Risiken“:

  1. Deployer-Identität verifizieren: SETUP_TOKEN eingeben (erscheint nur im Deploy-Output, nach Setup ungültig) — verhindert Panel-Übernahme.
  2. Admin-Zugangsdaten erstellen: Benutzername + Passwort mit ≥8 Zeichen (PBKDF2-gehasht, nicht wiederherstellbar).
  3. Email Routing aktivieren: lokal überspringen; in Produktion der Anleitung im Cloudflare-Dashboard folgen (nächster Abschnitt).
  4. Zieladresse hinzufügen: deine echte Mailbox (z. B. Gmail) eingeben und Cloudflare-Bestätigung abschließen.
  5. Erste Regel erstellen: standardmäßig *@yourdomain → weiterleiten → verifizierte Zieladresse, und setzt sie als Fail-open-Fallback.

4. E-Mail-Routing aktivieren (pro Domain)

Drei Dinge müssen vorhanden sein: der Email-Routing-Hauptschalter, catch-all auf den Worker gerichtet und eine verifizierte Zieladresse. Zwei Wege:

Option A · Panel-Automatisierung (empfohlen)

Nach dem Speichern eines CF-API-Tokens unter Einstellungen → Domains erscheint pro Domain ein „Weiterleitung aktivieren“-Button. Das Panel: erkennt MX-Konflikte (listet sie zur Bestätigung pro Eintrag) → aktiviert Email Routing → fügt empfohlene MX/SPF-DNS hinzu → richtet catch-all auf den InboxFly Worker.

Token-Berechtigungen (feldgetestet): Konto → Workers Scripts / D1 / KV / R2 Storage (Bearbeiten) + Kontoeinstellungen (Lesen); Zone → Zone (Lesen), DNS (Bearbeiten), Email Routing Rules (Bearbeiten), Zone Settings (Bearbeiten). Hinweis: Aktivieren/Abfragen von Email Routing erfordert die Gruppe „Zone Settings“, nicht „Email Routing Rules“ — beide ankreuzen, sonst Authentication error.

Option B · Manuell im Cloudflare-Dashboard

Dashboard → deine Zone → Email → Email Routing → Aktivieren (MX-Ersetzung bestätigen) → Catch-all-Adresse → Aktion „Send to a Worker“ → inboxfly wählen. Danach Panel aktualisieren; alle Domain-Checks werden grün.

5. Zieladressen

  • Füge auf der Zieladressen-Seite deine echte Mailbox hinzu → Cloudflare sendet automatisch eine Bestätigungsmail → nach dem Klick des Empfängers wird das Panel automatisch „Verifiziert“.
  • Zieladressen sind kontoweit: einmal verifizieren, überall nutzen.
  • Die erste verifizierte Adresse wird zum Fail-open-Fallback: Der Worker versucht sie bei internen Fehlern, um stillen Verlust zu vermeiden.
  • Von Regeln referenzierte Adressen können nicht gelöscht werden (du wirst gebeten, zuerst die Regel zu bearbeiten).

6. Routing-Regeln

Die Regelseite spiegelt Cloudflares native Routing-Seite: eine einheitliche Regel-Tabelle mit fester „📌 Catch-all“-Fallback-Zeile am Ende.

Regel erstellen

  • E-Mail-Match: Name links (z. B. info, support) + @ + Domain-Dropdown rechts; leerer Name = ganze Domain.
  • Aktion: An E-Mail senden (an verifizierte Zieladresse weiterleiten) / Verwerfen (still) / Zurückweisen (InboxFly-Erweiterung — SMTP-Ablehnung, nativ nicht verfügbar).
  • Erweiterte Filter (optionale Erweiterungen): Absender-Blacklist (eine pro Zeile: Adresse / @domain / /regex/), Betreff-Regex, Größenlimit (≤25MB), Anhang-Bedingung.

Auswertungsreihenfolge

Exakte Regeln → Catch-all-Regeln, in der Gruppe sortiert, first match wins. Nicht gematchte Mail geht an die Catch-all-Zeile (an Standard weiterleiten / zurückschicken / verwerfen).

Wichtig: Erstelle keine Routing-Regeln manuell im Cloudflare-Dashboard — native Regeln haben Vorrang vor catch-all und umgehen InboxFly (keine Kopien, keine Statistiken). Importiere vorhandene native Regeln über Einstellungen → Domains.

7. Tägliche Verwaltung

  • Mail-Liste: nach Domain / Status / Stichwort filtern; Batch-Mehrfachauswahl-Löschen unterstützt.
  • Mail-Details: Sandbox-HTML-Rendering (Remote-Bilder blockiert), Klartextanzeige, Anhang-Downloads, Roh-MIME (.eml).
  • Statistiken: nach Status (weitergeleitet/blockiert/verworfen/zurückgewiesen/Fehler) und Domain, mit 14-Tage-Trends. „Weitergeleitet“ = Cloudflare hat die Weiterleitung angenommen; die endgültige Platzierung ist nicht beobachtbar.
  • Layout: Der Button oben rechts wechselt zwischen Seitenleisten-/Header-Modus; mobil wird immer das Header-Layout verwendet.

8. Speicher & Kontingente

  • Kopien (HTML/Text/Roh-MIME) und Anhänge liegen in deinem eigenen R2, standardmäßig 30 Tage mit täglicher 03:00-UTC-Auto-Bereinigung (in den Einstellungen anpassbar; manuelle Bereinigung verfügbar).
  • Von Filtern blockierte Mail speichert standardmäßig nur Metadaten (spamflutsicher); bei Bedarf volle Texte aktivieren.
  • Ein Warnbanner erscheint, wenn die 30-Tage-R2-Schätzung 9GB übersteigt, mit Ein-Klick-Wechsel in den Metadaten-Modus (Weiterleitung unberührt).

9. Sicherheit

  • Cloudflare Turnstile: Einstellungen → Bot-Schutz, Site-/Secret-Schlüssel einfügen und aktivieren — eine Mensch-Prüfung erscheint beim Login (serverseitiges siteverify). Für lokale Tests die offiziellen Test-Schlüssel: Site 1x00000000000000000000AA / Secret 1x0000000000000000000000000000000AA (immer erfolgreich).
  • Admin-Konto: Einstellungen → Admin-Konto; Änderung von Benutzername/Passwort macht alle anderen Sitzungen ungültig.
  • Sitzungen: 24h Standard, 30 Tage mit „angemeldet bleiben“; CSRF-Schutz bei Änderungen, ratenlimitierter Login.
  • Sicherheit des Mail-Inhalts: Texte werden in einer iframe-Sandbox gerendert (Skripte deaktiviert), serverseitige Bereinigung entfernt gefährliches Markup, Remote-Bilder standardmäßig blockiert.

10. Designs / Sprache / PWA

  • 3 Designs × hell/dunkel: Fluid Glass (Standard) / Minimal / Playful, jeweils mit vollständiger Dunkelvariante; folgt standardmäßig dem System.
  • 10 Sprachen: automatisch aus dem Browser erkannt; jederzeit über das Globus-Symbol umschaltbar.
  • PWA-Installation: Android Chrome → Menü „App installieren“ (oder Einstellungen-Button); iOS Safari → Teilen → „Zum Home-Bildschirm“.

11. Bekannte Grenzen

  • Lokal können keine echten E-Mails empfangen werden (Email Routing ist eine Produktionsfunktion) — lokal „Simulieren“ verwenden.
  • „Weitergeleitet“ bedeutet, dass Cloudflare es angenommen hat; die Platzierung im Spam-Ordner ist nicht beobachtbar. Whiteliste deine Domain bei Bedarf in der Empfänger-Mailbox.
  • Mische native Cloudflare-Regeln und InboxFly nicht auf derselben Domain (sie umgehen das Panel); Koexistenz auf Zonen-Ebene ist in Ordnung.
  • 25MiB pro Nachricht (Cloudflare-Plattformlimit).

12. Deinstallation & Bereinigung

  1. Widerrufe das CF-API-Token des Panels (Dashboard → API-Tokens) — die Weiterleitungs-Pipeline läuft unabhängig in deinem Konto weiter; die Panel-Automatisierung degradiert.
  2. Weiterleitung stoppen: Dashboard → Email Routing → Catch-all oder den ganzen Dienst deaktivieren.
  3. Ressourcen löschen: Workers → inboxfly; D1 → inboxfly; R2 → inboxfly; KV → den Namespace.

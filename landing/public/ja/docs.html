1. ローカルで始める（3分）

ローカル環境では実際のメール受信はできませんが、パネルとパイプライン一式を試せます（「シミュレート」でテストデータを投入）：

git clone https://github.com/INBOXFLY-REPO-PLACEHOLDER/inboxfly.git
cd inboxfly && npm install
npm run dev          # 启动在 http://localhost:8787
  • 初回アクセスでセットアップウィザードが開きます。ローカル SETUP_TOKEN は inboxfly-local-setup（.dev.vars 参照）。
  • ウィザード手順3（Email Routing 有効化）はローカルではスキップ。
  • パネルの「シミュレート」：本番と同一のパイプライン（マッチ→フィルタ→判定→保存→統計）でテストメールを投入し、実際の配信のみスキップ。
  • リセット：rm -rf .wrangler 後に再起動してウィザードを再度実行。

2. Cloudflare にデプロイ

npx wrangler login
npx wrangler deploy           # Worker + 静态面板 + D1 + R2 + KV + Cron
npx wrangler secret put SETUP_TOKEN    # 首次运行向导用的初始化令牌
  • D1 テーブルは初回アクセス時に自動作成（手動 SQL 不要。フォールバックとして npx wrangler d1 execute inboxfly --remote --file schema.sql も可）。
  • パネルは https://inboxfly.<サブドメイン>.workers.dev が既定。Workers → Domains & Routes でカスタムドメイン（例 panel.yourdomain）を設定推奨。
  • Cron Trigger（毎日 03:00 UTC の R2 クリーンアップ）はデプロイ時に自動登録。
  • robots.txt に Disallow: / が含まれ、プライベートパネルはインデックスされません。

3. 初回ウィザード（5ステップ）

デプロイ後にパネル URL を開き、ウィザードに従います。各ステップで「理由」と「リスク」を説明します：

  1. デプロイ者の確認：SETUP_TOKEN を入力（デプロイ出力のみに表示、設定完了後に無効化）—パネル乗っ取り防止。
  2. 管理者認証情報の作成：ユーザー名 + 8文字以上のパスワード（PBKDF2 ハッシュ、復元不可）。
  3. Email Routing の有効化：ローカルではスキップ。本番では Cloudflare ダッシュボードの案内に従う（次節）。
  4. 宛先アドレスの追加：実メールボックス（例 Gmail）を入力し、Cloudflare の確認を完了。
  5. 最初のルールを作成：既定 *@yourdomain → 転送 → 確認済み宛先、fail-open フォールバックとして設定。

4. メールルーティングの有効化（ドメインごと）

必要なのは3つ：Email Routing マスタースイッチ、Worker を指す catch-all、確認済みの宛先。2つの方法：

方法A · パネル自動化（推奨）

設定 → ドメインで CF API トークンを保存すると、ドメインごとに「転送を有効化」ボタンが表示。パネルが自動で：MX 競合の検出（一覧表示してレコードごとに確認）→ Email Routing 有効化 → 推奨 MX/SPF DNS 追加 → catch-all を InboxFly Worker に設定。

トークン権限（実測済み）：Account → Workers Scripts / D1 / KV / R2 Storage（編集）+ Account Settings（読み取り）；Zone → Zone（読み取り）、DNS（編集）、Email Routing Rules（編集）、Zone Settings（編集）。注意：Email Routing の有効化/照会には「Zone Settings」グループが必要で「Email Routing Rules」では不足 — 両方オンにしないと Authentication error。

方法B · Cloudflare ダッシュボードで手動

ダッシュボード → ゾーン → Email → Email Routing → 有効化（MX 置換を確認）→ Catch-all アドレス → アクション「Send to a Worker」→ inboxfly を選択。後にパネルを更新するとドメインの健全性チェックがすべて緑に。

5. 宛先アドレス

  • 宛先ページで実メールボックスを追加 → Cloudflare が確認メールを自動送信 → 受信者がクリックすると自動的に「確認済み」に。
  • 宛先はアカウント単位：一度確認すれば全ドメインで使用可能。
  • 最初の確認済みアドレスがfail-open フォールバックになります：Worker が内部エラー時に試行し、無音の損失を防止。
  • ルールが参照するアドレスは削除不可（先にルールを編集するよう求められます）。

6. ルーティングルール

ルールページは Cloudflare のルーティングページを踏襲：統一ルール表＋末尾に固定の「📌 Catch-all」フォールバック行。

ルールの作成

  • メールマッチ：左に名前（例 info、support）+ @ + 右にドメイン選択。名前空欄 = ドメイン全体。
  • アクション：メールへ送信（確認済み宛先へ転送）/ 破棄（サイレント）/ バウンス（InboxFly 拡張 — SMTP レベル拒否、ネイティブにはなし）。
  • 高度なフィルタ（任意拡張）：送信者ブラックリスト（1行1件：アドレス / @ドメイン / /正規表現/）、件名正規表現、サイズ上限（≤25MB）、添付条件。

評価順序

正確ルール → catch-all ルール、グループ内でソート、先にマッチしたものが勝ち。未マッチは Catch-all 行（既定宛先へ転送/バウンス/破棄）。

重要：Cloudflare ダッシュボードで手動ルーティングルールを作成しないでください — ネイティブルールは catch-all より優先され InboxFly をバイパス（コピーも統計もなし）。既存ネイティブルールは 設定 → ドメイン からインポート。

7. 日常管理

  • メールリスト：ドメイン/ステータス/キーワードで絞り込み、一括選択削除対応。
  • メール詳細：サンドボックス HTML レンダリング（リモート画像ブロック）、プレーンテキスト表示、添付ダウンロード、生 MIME（.eml）。
  • 統計：ステータス（転送/ブロック/破棄/バウンス/エラー）とドメイン別、14日トレンド。「転送済み」＝ Cloudflare が受理したことを意味し、最終配置は観測不可。
  • レイアウト：右上ボタンでサイドバー/ヘッダーモード切替。モバイルは常にヘッダーレイアウト。

8. ストレージとクォータ

  • コピー（HTML/テキスト/生 MIME）と添付はあなたの R2に保存、既定30日保持で毎日 03:00 UTC 自動クリーンアップ（設定で調整可、手動クリーンアップも可）。
  • フィルタでブロックされたメールは既定メタデータのみ保存（スパムストーム対策）。必要時に本文保存を有効化。
  • 30日 R2 見積が 9GB を超えると警告バナーが表示され、ワンクリックでメタデータのみモードへ（転送には影響なし）。

9. セキュリティ

  • Cloudflare Turnstile：設定 → ボット対策で Site/Secret キーを貼って有効化 — サインイン時に人間確認が表示（サーバー側 siteverify）。ローカルテスト用の公式テストキー：Site 1x00000000000000000000AA / Secret 1x0000000000000000000000000000000AA（常に成功）。
  • 管理者アカウント：設定 → 管理者アカウント。ユーザー名/パスワード変更で他セッションは全て無効化。
  • セッション：既定24時間、「ログイン状態を保持」で30日。変更系は CSRF 保護、ログインはレート制限。
  • メール内容の安全性：本文は iframe サンドボックス（スクリプト無効）でレンダリング、サーバー側サニタイズで危険マークアップ除去、リモート画像は既定でブロック。

10. テーマ/言語/PWA

  • 3テーマ × ライト/ダーク：Fluid Glass（既定）/ Minimal / Playful、各フルダーク版。既定でシステム追従。
  • 10言語：ブラウザから自動検出。地球アイコンでいつでも切替。
  • PWA インストール：Android Chrome → メニュー「アプリをインストール」（または設定ボタン）。iOS Safari → 共有 → 「ホーム画面に追加」。

11. 既知の制限

  • ローカルは実メール受信不可（Email Routing は本番機能）— ローカルでは「シミュレート」を使用。
  • 「転送済み」は Cloudflare が受理した意味。スパムフォルダ配置は観測不可。必要なら受信メールボックスでドメインを許可。
  • 同一ドメインで Cloudflare ネイティブルールと InboxFly を混在させない（パネルをバイパスします）。ゾーン単位の併存は問題なし。
  • メッセージあたり 25MiB（Cloudflare プラットフォーム制限）。

12. アンインストールとクリーンアップ

  1. パネルの CF API トークンを失効（ダッシュボード → API トークン）— 転送パイプラインはあなたのアカウントで独立稼働し続けます。パネル自動化は縮退。
  2. 転送停止：ダッシュボード → Email Routing → Catch-all または全体を無効化。
  3. リソース削除：Workers → inboxfly；D1 → inboxfly；R2 → inboxfly；KV → 名前空間。

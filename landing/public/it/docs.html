1. Avvio rapido in locale (3 min)

Gli ambienti locali non possono ricevere email reali, ma puoi testare l’intero pannello e la pipeline (dati tramite « Simula »):

git clone https://github.com/INBOXFLY-REPO-PLACEHOLDER/inboxfly.git
cd inboxfly && npm install
npm run dev          # 启动在 http://localhost:8787
  • La prima visita apre l’assistente di configurazione; il SETUP_TOKEN locale è inboxfly-local-setup (vedi .dev.vars).
  • Il passaggio 3 dell’assistente (Attiva Email Routing) viene saltato localmente.
  • Nel pannello clicca su « Simula »: inserisce email di test tramite esattamente la pipeline di produzione (corrispondenza → filtro → decisione → archiviazione → statistiche), saltando solo la consegna reale.
  • Per reimpostare: rm -rf .wrangler e riavvia, poi rifai l’assistente.

2. Deploy su Cloudflare

npx wrangler login
npx wrangler deploy           # Worker + 静态面板 + D1 + R2 + KV + Cron
npx wrangler secret put SETUP_TOKEN    # 首次运行向导用的初始化令牌
  • Le tabelle D1 vengono create automaticamente alla prima visita del pannello — nessun SQL manuale richiesto (o esegui npx wrangler d1 execute inboxfly --remote --file schema.sql come ripiego).
  • Il pannello è per impostazione predefinita a https://inboxfly.<tuo-sottodominio>.workers.dev; collega un dominio personalizzato (es. panel.yourdomain) in Workers → Domains & Routes.
  • Il Cron Trigger (pulizia R2 giornaliera alle 03:00 UTC) viene registrato automaticamente con il deploy.
  • robots.txt include Disallow: / così il tuo pannello privato non viene indicizzato.

3. Assistente di prima esecuzione (5 passaggi)

Apri l’URL del pannello dopo il deploy e segui l’assistente. Ogni passaggio spiega « perché » e « rischi »:

  1. Verifica dell’identità del deployer: inserisci il SETUP_TOKEN (appare solo nell’output del deploy, invalidato dopo la configurazione) per prevenire la presa di controllo.
  2. Creare le credenziali admin: nome utente + password ≥8 caratteri (hash PBKDF2, non recuperabile).
  3. Attiva Email Routing: salta in locale; in produzione segui la guida nel dashboard Cloudflare (sezione successiva).
  4. Aggiungi un indirizzo di destinazione: inserisci la tua vera casella email (es. Gmail) e completa la conferma Cloudflare.
  5. Crea la prima regola: per impostazione predefinita *@yourdomain → inoltra → destinazione verificata, e la imposta come fallback fail-open.

4. Attivare il routing email (per dominio)

Tre elementi devono essere presenti: l’interruttore principale Email Routing, il catch-all che punta al Worker e una destinazione verificata. Due modi:

Opzione A · Automazione dal pannello (consigliata)

Dopo aver salvato un token API CF in Impostazioni → Domini, appare un pulsante « Attiva inoltro » per dominio. Il pannello: rileva i conflitti MX (li elenca per conferma per record) → attiva Email Routing → aggiunge i record DNS MX/SPF consigliati → punta catch-all al Worker InboxFly.

Permessi del token (testati): Account → Workers Scripts / D1 / KV / R2 Storage (Modifica) + Impostazioni account (Lettura); Zone → Zone (Lettura), DNS (Modifica), Email Routing Rules (Modifica), Zone Settings (Modifica). Nota: attivare/interrogare Email Routing richiede il gruppo « Zone Settings », non « Email Routing Rules » — spunta entrambi altrimenti errore Authentication.

Opzione B · Manualmente nel dashboard Cloudflare

Dashboard → zona → Email → Email Routing → Attiva (conferma la sostituzione MX) → Indirizzo catch-all → azione « Send to a Worker » → scegli inboxfly. Aggiorna poi il pannello; tutti i controlli diventano verdi.

5. Indirizzi di destinazione

  • Aggiungi la tua vera casella email nella pagina Destinazioni → Cloudflare invia automaticamente un’email di conferma → appena il destinatario clicca, il pannello passa a « Verificato ».
  • Le destinazioni sono a livello di account: verifica una volta, usa ovunque.
  • Il primo indirizzo verificato diventa il fallback fail-open: il Worker lo tenta in caso di errori interni per evitare perdite silenziose.
  • Gli indirizzi referenziati dalle regole non possono essere eliminati (ti verrà chiesto di modificare prima la regola).

6. Regole di routing

La pagina delle regole rispecchia la pagina di routing nativa di Cloudflare: una tabella unificata con una riga di fallback fissa « 📌 Catch-all » in fondo.

Creare una regola

  • Corrispondenza email: nome a sinistra (es. info, support) + @ + elenco domini a destra; nome vuoto = intero dominio.
  • Azione: Invia a un’email (inoltra a una destinazione verificata) / Elimina (silenzioso) / Rimbalza (miglioramento InboxFly — rifiuto a livello SMTP, non nativo).
  • Filtri avanzati (miglioramenti opzionali): blacklist mittente (uno per riga: indirizzo / @dominio / /regex/), regex oggetto, limite dimensione (≤25MB), condizione allegato.

Ordine di valutazione

Regole esatte → regole catch-all, ordinate nel gruppo, primo match vince. Le email non corrisposte vanno alla riga Catch-all (inoltra per default / rimbalza / elimina).

Importante: non creare regole di routing manualmente nel dashboard Cloudflare — le regole native hanno precedenza su catch-all e bypassano InboxFly (niente copie, niente statistiche). Importa le regole native esistenti tramite Impostazioni → Domini.

7. Gestione quotidiana

  • Elenco email: filtro per dominio / stato / parola chiave; eliminazione batch multi-selezione supportata.
  • Dettaglio email: rendering HTML sandbox (immagini remote bloccate), visualizzazione testo, download allegati, MIME grezzo (.eml).
  • Statistiche: per stato (inoltrata/bloccata/eliminata/rimbalzata/errore) e dominio, con tendenze a 14 giorni. « Inoltrata » = Cloudflare ha accettato l’inoltro; il posizionamento finale non è osservabile.
  • Layout: il pulsante in alto a destra alterna modalità barra laterale / intestazione; il mobile usa sempre il layout intestazione.

8. Archiviazione e quote

  • Le copie (HTML/testo/MIME grezzo) e gli allegati vivono nel tuo R2, conservati 30 giorni per default con pulizia automatica giornaliera alle 03:00 UTC (regolabile in Impostazioni; pulizia manuale disponibile).
  • Le email bloccate dai filtri archiviano solo metadati per default (anti-tempesta di spam); attiva i corpi completi se serve.
  • Un banner di avviso appare quando la stima R2 a 30 giorni supera 9GB, con passaggio in un clic alla modalità solo metadati (inoltro invariato).

9. Sicurezza

  • Cloudflare Turnstile: Impostazioni → Protezione anti-bot, incolla le chiavi Site/Secret e attiva — appare una verifica umana al login (siteverify lato server). Per i test locali, chiavi di test ufficiali: Site 1x00000000000000000000AA / Secret 1x0000000000000000000000000000000AA (sempre valido).
  • Account admin: Impostazioni → Account admin; cambiare nome/password invalida tutte le altre sessioni.
  • Sessioni: 24h per default, 30 giorni con « rimani connesso »; protezione CSRF sulle modifiche, login limitato.
  • Sicurezza del contenuto: i corpi sono renderizzati in una sandbox iframe (script disattivati), la sanificazione server rimuove il markup pericoloso, immagini remote bloccate per default.

10. Temi / lingua / PWA

  • 3 temi × chiaro/scuro: Fluid Glass (default) / Minimal / Playful, ognuno con variante scura completa; segue il sistema per default.
  • 10 lingue: rilevamento automatico dal browser; cambio in qualsiasi momento tramite l’icona globo.
  • Installazione PWA: Android Chrome → menu « Installa app » (o pulsante Impostazioni); iOS Safari → Condividi → « Aggiungi a schermata Home ».

11. Limiti noti

  • Il locale non può ricevere email reali (Email Routing è una funzionalità di produzione) — usa « Simula » in locale.
  • « Inoltrata » significa che Cloudflare l’ha accettata; il posizionamento nella cartella spam non è osservabile. Metti il tuo dominio in whitelist nella casella del destinatario se serve.
  • Non mescolare regole native Cloudflare e InboxFly sullo stesso dominio (bypassano il pannello); la coesistenza a livello di zona è senza problemi.
  • 25MiB per messaggio (limite della piattaforma Cloudflare).

12. Disinstallazione e pulizia

  1. Revoca il token API CF del pannello (dashboard → Token API) — la pipeline di inoltro funziona indipendentemente nel tuo account e continua; l’automazione del pannello si degrada.
  2. Fermare l’inoltro: dashboard → Email Routing → disattiva Catch-all o l’intero servizio.
  3. Elimina le risorse: Workers → inboxfly; D1 → inboxfly; R2 → inboxfly; KV → il namespace.
Se qualcosa non è coperto qui, apri un ticket GitHub (link del repo sulla pagina prodotto).
